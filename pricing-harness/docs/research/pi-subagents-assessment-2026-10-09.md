# pi-subagents assessment — 9 October 2026

Recommendation: retain the current launcher while testing compact intake and batched calculations. Consider `pi-subagents` later as an orchestration dependency if reducing custom lifecycle code is valuable. No plugin installation, migration or performance test was performed.

The extension supports narrow child agents with explicit tools, selected skills, output paths and thinking settings. Children can start with fresh context rather than inheriting the parent history. These are useful controls for pricing roles, although our existing workers already use separate fresh sessions and tool allowlists. [Agent documentation](https://github.com/nicobailon/pi-subagents/blob/main/docs/agents.md)

Its structured delegation API returns schema-validated values, reconciled usage and explicit logical-node identities, with exact cancellation identities and duplicate-active-node handling. This could replace some launch/result plumbing. Schema validation establishes payload shape; our raw-source provenance, independent numerical checks, held facts and checkpoint integrity would still be application responsibilities. [Extension API](https://github.com/nicobailon/pi-subagents/blob/main/docs/extension-api.md)

Scripted workflows support sequential chains and concurrent independent child work. Our present verifier takes analyst claim IDs and candidate output, so starting those existing stages concurrently would require changing the evidence protocol. A possible future design is two independent calculations from the same scoped work order, followed by deterministic comparison; that is an architectural change rather than a launcher setting. [Workflow documentation](https://github.com/nicobailon/pi-subagents/blob/main/docs/workflows.md)

Integration is not a drop-in package install: `createPricingSession` disables extensions, `StageRunner` owns process cancellation and shared budget gates, and `execute_analysis` is a harness-owned provenance tool. An adapter must preserve those controls, register the required child tools, verify compatibility with our pinned Pi SDK 1.0.4, and enforce the chosen DeepSeek/high settings for every role. The repository currently develops against Pi packages 0.87.0; that is a compatibility test requirement, not proof of incompatibility. [Package metadata](https://github.com/nicobailon/pi-subagents/blob/main/package.json)

The performance assessment is an inference from the supported mechanisms and our measured trace: switching launchers alone provides no demonstrated reduction in model turns, raw-file context growth or output serialization. The measured bottleneck was time inside model requests, not child-process startup. Fix those interactions first, then compare launchers under the same work order, model, reasoning, source versions and verification requirements if a migration is still worthwhile.
