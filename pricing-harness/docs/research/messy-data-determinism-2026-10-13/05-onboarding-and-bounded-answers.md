# 05. Workspace onboarding, defects as decisions, bounded answers

Date: 2026-10-13. Workstream 5. Builds on 01 (curated context beats prompts; ablation of knowledge layers), 02 (issue register with stable IDs, default vocabulary) and 03 (prepared view, drafted-then-confirmed semantic model). Those are not repeated here.

Labels: **[vendor]** = vendor documentation or claim; **[measured]** = benchmark or ablation in a paper; **[secondary]** = third-party write-up or search summary I could not check against the primary text; **[mine]** = my inference, not in any source.

## 1. Summary

- **A short onboarding step pays off only if the map holds what code cannot infer, plus pointers to the rest.** No study isolates "workspace onboarding interview" for a data agent. The indirect evidence points one way: curated definitions, keys and examples help ([Databricks ablation, in 01], [dbt study, in 03]). Generic, LLM-written overviews do not help coding agents and cost over 20 % more inference ([AGENTS.md study, measured](https://arxiv.org/abs/2602.11988)). So the map should be small, factual and mostly generated by code.
- **Every product that has this idea splits it in two.** A small always-on context (Hex: about 300 lines at most; Claude Code: loaded each session) and a larger set of on-demand notes found by a short trigger description (Hex guides, Devin Knowledge, Cursor "Apply Intelligently", Claude Code topic files). That is the routing mechanism to copy. [vendor]
- **Auto-drafted metadata is always reviewed by a person, and reviewing is where products struggle.** Snowflake found that setup overhead suppressed usage and that 50 separate suggestions caused decision fatigue ([engineering blog](https://www.snowflake.com/en/engineering-blog/using-ai-improving-ai/), [vendor]). The interview must therefore be short and pre-filled: confirm proposed answers, do not ask open questions.
- **Ask lazily for most things.** Databricks, Hex and MotherDuck all advise starting with little and adding context when a real failure appears. Only measure-level facts (which field is revenue, which currency, how credits and rebates are treated) are needed before the first question. Defect handling can be asked at first contact, with a default pre-selected, and then stored.
- **Freshness is cheap if every map entry carries the content hash of what it was derived from.** A changed file invalidates only the entries derived from it. Decisions are keyed by a stable defect ID and flagged for reconfirmation when their evidence changes, not silently reused.
- **A defect becomes a decision when it has a stable ID, a policy from a fixed vocabulary, a scope and a provenance line, and code (not the prompt) applies it.** No surveyed system does this for analytic defects end to end; data-contract tools hold the rules and thresholds, not the analyst's handling choice.
- **Ask, assume or bound should be decided by the effect on the answer, not by the model's feeling of uncertainty.** Prompting alone makes models over-ask or ask vague questions ([CIGAsk, search summary](https://arxiv.org/abs/2609.24290), [secondary]); uncertainty-gated asking beat a standard agent 69.4 % to 61.2 % on underspecified SWE-bench tasks ([Ask or Assume](https://arxiv.org/abs/2603.26233), [measured]). In our setting code can compute the answer under each handling and see whether it changes.
- **When data is missing, a bounded answer is usually available and cheaper than holding.** Worst-case (Manski) bounds need only the known range of the unknown quantity; the interval width equals the missing share times the range. For "which SKU is highest" the winner is provable if its lower bound beats every rival's upper bound [mine, built on the bounds].

### Measured evidence on context

- [Evaluating AGENTS.md (arXiv 2602.11988, ICLR 2026)](https://arxiv.org/abs/2602.11988) [measured]: context files "do not generally improve" task success and raise inference cost by over 20 %; repository overviews are not helpful; context files are useful for non-standard practices. Secondary summaries put LLM-written files at about -2 % and human-written at about +4 %; I could not confirm those figures in the primary text.
- [Wretblad et al., synthetic column descriptions (arXiv 2408.04691)](https://arxiv.org/abs/2408.04691) [measured, BIRD benchmark]: detailed descriptions raise text-to-SQL accuracy mainly where column names are uninformative; models struggle with inherently ambiguous columns, so expert input is still needed.
- [MotherDuck session on DABstep sample data](https://motherduck.com/videos/context-management-data-agents/) [vendor, relative rankings only]: plain English context did best, SQL question-answer pairs matched it and ran faster on similar questions, semantic-model languages did worst. Advice: skip obvious columns, avoid negative instructions, start from a blank file and add context for observed failures.
- [Plotly guide](https://plotly.com/blog/guide-to-data-context-in-the-age-of-ai/) [vendor, qualitative, no experiments]: agentic exploration worked better than an upfront summary for the data itself, but does not teach internal terminology or norms.
- [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [vendor]: keep lightweight references, load on demand, hybrid of upfront and exploration, persistent notes outside the window.
- [Agent Workflow Memory](https://arxiv.org/abs/2409.07429) [measured, web agents]: induced reusable workflows raised relative success by 24.6 % (Mind2Web) and 51.1 % (WebArena); not data analysis, and the 51.1 % figure is, per a secondary summary, against the strongest prior autonomous method. [Data-management view of agent memory](https://arxiv.org/abs/2606.24775) [measured, 12 systems]: no memory architecture wins everywhere and localized maintenance is cheaper than global reorganization.

## 3. Patterns

### P1. A two-layer map: machine-derived facts and human-confirmed decisions

*Moves from LLM to code:* source inventory, grain and key candidates, join candidates, period coverage, issue register (the content of 02). The model stops rediscovering these.
*Evidence:* Genie knowledge mining and Autopilot infer keys, joins and value lists from metadata and data, then ask for review [vendor]. Wave-1 files show the stepwise value of keys and defined metrics [vendor ablation].
*Cost:* low. The profiler already exists in design (02); the map is its summary plus hashes.

**What it holds** (one record per source, plus workspace-level sections):

| Section | Content | Inferred by code? | Must be asked? |
|---|---|---|---|
| Source inventory | file, content hash, rows, columns with type, size | Yes | No |
| Grain and keys | candidate key, uniqueness %, violators | Yes (02 P2) | Confirm only if ambiguous |
| Joins | FK candidate, containment %, fan-out risk | Yes (02 P3) | No |
| Period | min/max date, last-period completeness, as-of date | Yes | Fiscal calendar if not calendar |
| Field-to-measure mapping | proposed revenue/cost/quantity/price columns, from names, types, and notes | Proposed by code or LLM | **Yes, confirm** |
| Currency and units | base currency, per-field unit values seen | Detect conflicts (02 P7) | **Yes: reporting currency and treatment of off-base rows** |
| Accounting treatment | credits, returns, rebates, whether margin is net of rebates | Sign mix detected | **Yes** |
| Authority between sources | which note or table wins on conflict | No | **Yes, one question** |
| Defect register with handling | issue ID, class, counts, policy, decided by | Detection yes | Handling: default, confirm at first contact |
| Document index | note ID, hash, headings, one-line "use when" description, key terms | Headings and terms by code; description by LLM once per hash | No, flag as unreviewed |

Keep it small. Hex caps always-on context at roughly 300 lines and puts metric definitions in retrievable guides; MotherDuck says to drop obvious columns [vendor]. The AGENTS.md result is the warning: do not generate a descriptive overview of things the agent can see (column names, file lists) [measured].

### P2. Short, pre-filled interview

*Moves from LLM to code:* proposing the answers. The model or code drafts the mapping; the user only confirms or corrects.
*Evidence:* Google and Genie both tell authors to review the generated context before customising [vendor]; Snowflake's decision-fatigue finding argues against many small decisions [vendor]. No source measures the best number of questions, so the number below is my judgement [mine].
*Cost:* low. This is `pricing-intake` with code-built defaults.

Recommended interview, in order of value (stop when the user stops; each has a pre-selected default):

1. **Measures.** "Revenue = `net_sales`, cost = `unit_cost_gbp` x `qty`, margin = revenue - cost. Correct?" One card, three to five fields.
2. **Reporting currency and units.** "Report in GBP. 312 cost rows are EUR and 4,100 are PACK. Convert / exclude / flag?" (default: exclude from cost coverage and bound; see P6).
3. **Credits, returns, rebates.** Include negative-quantity lines in margin? Allocate customer-level rebates or report separately? Defaults from the bundled policy.
4. **Period conventions.** As-of date taken from the data, last period partial, "complete quarter" rule.
5. **Which note wins** when policy notes disagree with data (only if the note index finds a conflict).

Everything else (individual defects such as a duplicate master key or a `POST` SKU) is asked at first contact, as a default-accept confirmation, then stored (P3). This follows "add instructions gradually from real use" ([Databricks blog](https://databricks.com/blog/5-key-lessons-implementing-aibi-genie-self-service-marketing-insights)) and MotherDuck's "start blank, add for observed failures" [vendor].

### P3. Defect decision store

*Moves from LLM to code:* the handling choice and its application. The prepared view (03 rec. 1) applies the policy; the model is told which policy applied and cannot reinterpret it.
*Evidence:* Genie trusted assets and Cortex verified queries reuse approved logic for consistency [vendor]; the nondeterminism literature argues for confining the stochastic step and recording what was applied ([Confining Nondeterminism](https://www.alphaxiv.org/abs/2607.10508), proposal only). No benchmark shows a decision store reduces run-to-run variance; the reasoning is direct, since the model no longer chooses.
*Cost:* low to moderate.

Record shape (lives in `.pricing/context.md` as a machine-readable section, or a YAML sibling):

- `id`: hash of (source, column or key, defect class), stable across reruns
- `class` and `evidence`: counts and value at stake from the register
- `policy`: from a fixed vocabulary, e.g. `exclude`, `dedupe_exact`, `keep_first`, `convert`, `flag_unusable`, `bound`, `accept_as_is`
- `decided_by`: `default` or `user`, with date
- `scope`: workspace-wide or this source only
- `source_hash`: the version the decision was made against
- `note`: one line of rationale

Precedence: user decision > bundled default for the class > ask. Bundled defaults are per defect class, not per dataset, so they stay general (for example: exact repeated rows are removed and counted; a key with duplicates is deduplicated only if the duplicates are identical, otherwise the join is flagged and the conflicting rows are bounded).

### P4. Retrieval of only relevant sources and notes

*Moves from LLM to code:* selecting what the analyst sees.
*Evidence:* Hex, Devin and Cursor retrieve guides by name and description [vendor]; Anthropic recommends lightweight references with on-demand loading [vendor]; wave-1 (01) records Hex stalls and OpenAI conflicts from too much context [secondary]. Hex notes that descriptions should contain the terms users type ("revenue", "AOV") [vendor].
*Cost:* low.

Per query: (1) code lexically matches question terms against column names, glossary terms, note descriptions and key terms; (2) the coordinator sees only the map index (about 1-2 KB: source IDs with one-line grain/measure summaries, note IDs with "use when" lines, open issue IDs) and writes the WorkOrder with source IDs, note IDs and issue IDs; (3) the analyst prompt is built from those slices only. Everything else stays on disk behind a lookup tool. Plotly's point applies: exploration is fine for the data itself, so the lookup tool should return sample rows and counts on demand [vendor, qualitative].

### P5. Hash-based freshness

*Moves from LLM to code:* deciding whether a stored fact is still true.
*Evidence:* dbt `state:modified` hashes small seed files and falls back to path comparison for large ones, and does not detect data changes in other node types ([dbt docs](https://docs.getdbt.com/reference/node-selection/state-comparison-caveats), [vendor]). The lesson: hash content directly, since our changes are data changes. The content-addressed, input-signature cache is described in [Confining Nondeterminism](https://www.alphaxiv.org/abs/2607.10508) (proposal). Hex, Devin and Autopilot all expect people to edit entries over time and log changes [vendor].
*Cost:* low.

Rules [mine]:

1. Each map entry stores the hashes of its inputs. On workspace open, compare file hashes (size+mtime as a fast path, full hash when they differ).
2. Changed file: recompute its inventory, keys, register entries. Entries that depend on it (joins, derived coverage) are marked stale and recomputed.
3. Decisions: if the same defect ID reappears, the decision applies and its `source_hash` is updated, but if the counts moved by more than a set ratio, flag "reconfirm". If the ID disappears, mark `resolved`. If a new ID appears, apply the class default and queue a confirm.
4. Changed note: re-index that note only; flag any decision or measure that cites it.
5. Schema change (column added, removed, retyped): invalidate measure mappings on that source and re-ask that one confirmation.

### P6. Bound-first answers

*Moves from LLM to code:* the arithmetic and the claim test.
*Evidence:* the identity is textbook ([Manski worst-case bounds](https://metricgate.com/docs/manski-bounds)): with observed share p, observed mean mu and unknown values in [a, b], the interval is [p*mu + (1-p)*a, p*mu + (1-p)*b], width (1-p)(b-a). Worst-case bounds are credible but often wide, and extra assumptions narrow them transparently; in one HIV-survey study the assumption-free bounds were not informative (as summarised in the explainer). For ranking data, [bracketing unobserved ranks with best-case and worst-case samples](https://arxiv.org/pdf/2207.07005) uses the same logic. Applying it to margin by SKU is my construction [mine].
*Cost:* low. DuckDB aggregates, no model.

Application: lines without an effective cost have known revenue and unknown cost. A cost range comes from that SKU's observed costs, else from a stated sign or ratio assumption, recorded as a decision. Each SKU then has a margin interval. The top-1 claim is **provable** if the leader's lower bound exceeds every other SKU's upper bound; otherwise report the set of SKUs that cannot be excluded, with the interval and the uncovered share. This replaces "hold the answer" with "answer with a proven statement". Results carry the interval, the uncovered population (rows and value) and the decision IDs applied.

### P7. Decision-relevance gate for ask / assume / bound

*Moves from LLM to code:* deciding whether a defect matters to this answer.
*Evidence:* uncertainty-gated questioning helps ([Ask or Assume](https://arxiv.org/abs/2603.26233), [measured], abstract only), prompting alone over-asks or asks vaguely ([CIGAsk](https://arxiv.org/abs/2609.24290), [secondary]), AmbiSQL gains came from detecting and resolving ambiguous phrases ([abstract](https://arxiv.org/abs/2508.15276)), and AmbigQA's alternative is to answer each reading. The sensitivity test itself is [mine].
*Cost:* moderate; needs the prepared view to recompute under each policy option.

Rule: for each issue touching the work order, code recomputes the headline figure under each allowed policy. If the answer (or the ranking) is the same, assume the stored or default policy and add a one-line disclosure. If it differs by less than the question's tolerance, assume and report a bound. If it differs materially and no user decision exists, ask once with the two numbers shown, then store. If a question can be read two ways (AmbigQA-style), compute both and show both only when cheap; otherwise ask. The abstention survey ([Wen et al.](https://arxiv.org/abs/2407.18418)) supports abstaining on the specific unanswerable figure; with bounds in place, abstention is rarely needed.

### P8. Provenance on every figure

*Moves from LLM to code:* the assumptions list. Each approved claim carries the decision IDs and source hashes it used; the reply footer is generated from them. Evidence: reasoned argument and the "evidence gate" design in [Confining Nondeterminism](https://www.alphaxiv.org/abs/2607.10508) (proposal). Cost: low, since delivery already binds figures to claim IDs (CONTEXT.md).

## 5. Recommendations (simplest first)

1. **Adopt: the code-built workspace map (P1) with hashes (P5).** Source inventory, grain/keys, joins, period, issue register, note index; at most 1-2 KB reaches a prompt, the rest sits on disk. Do not generate prose overviews.
2. **Adopt: the decision store (P3) with a fixed policy vocabulary and per-class bundled defaults.** Applied by the prepared view in code. Precedence user > default > ask.
3. **Adopt: a five-question interview with pre-filled answers (P2).** Measures, currency/units, credits and rebates, period, source authority. Defect-level confirmations happen at first contact.
4. **Adopt: retrieval by source and note IDs in the WorkOrder (P4).** Deterministic lexical matching proposes candidates; the coordinator chooses from the index; analyst and verifier see only the chosen slices.
5. **Adopt: bound-before-hold with a top-1 certification test (P6).** Directly addresses a documented failure. Keep the cost-range assumption as a recorded decision.
6. **Try: decision-relevance gate (P7).** Start with the single case of ranking stability; extend if useful. Measure how many questions it avoids and whether answers stay stable across runs.
7. **Try: one-line LLM descriptions for notes at upload, cached by hash, marked "unreviewed" (Atlan/DataHub pattern).** The model reads a note once, not every stage. Evidence is vendor-only; keep it behind the hash cache.
8. **Try: provenance footer from decision IDs (P8).**
9. **Try later: trusted/verified queries for questions the user accepts.** Gains consistency; no ablation (see 03).
10. **Skip: self-updating agent memory.** Autopilot, Devin and Genie propose changes for a person to approve; keep it that way. Memory papers show gains on web tasks and no universal winner ([AWM](https://arxiv.org/abs/2409.07429), [memory study](https://arxiv.org/abs/2606.24775)); none addresses analytic consistency.
11. **Skip: a full glossary or semantic-model authoring step at onboarding.** Heavy, and Plotly notes it pays off only with hundreds of concepts to disambiguate [vendor].
12. **Skip: asking about every detected defect up front.** Decision fatigue is a measured product finding at Snowflake [vendor].

## 6. Open questions and weak evidence

- **No controlled evidence for the interview itself.** I found no study comparing "onboarded" and "cold" data-agent runs on accuracy or latency. The case rests on analogy (Databricks, dbt, MotherDuck, Wretblad) and one negative result (AGENTS.md). The harness's six-turn conversation, run with and without the map on Luna, a Sonnet-class model and a Flash-class model, is the test to run.
- **The AGENTS.md result is on coding, not analytics, and the file types differ.** It may overstate the cost of context for our case, or understate it. The exact deltas for LLM-written vs human-written files come from secondary summaries.
- **Number of questions is my judgement.** No source measures it.
- **Julius, Cursor and Codex rows are secondary.** The ODCS and Great Expectations handling semantics were not checked at field level; I did not verify any published system that stores analyst-style defect decisions.
- **CIGAsk and BIRD-Interact ask-rate numbers were not retrievable** (the first PDF would not parse; the second abstract gives only completion rates).
- **Bounds need a defensible range.** For unknown costs the range is itself an assumption; if it is too wide, intervals are uninformative (the usual Manski criticism). The 2,138-line case likely has a narrow range per SKU, but that is untested.
- **Decision-relevance gate cost.** Recomputing under each policy may be expensive on 1 M rows; whether it fits the time budget is unmeasured.
- **Staleness thresholds** (when to reconfirm after count changes) are arbitrary until tried on real re-uploads.
