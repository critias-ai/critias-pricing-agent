# 06 Deterministic verification of analysis results

Date: 2026-10-13. Workstream 6. Builds on 01 (harness survey), 02 (profiling and issue register) and 03 (semantic layers). Evidence tags: **[measured]** = paper or benchmark result, **[vendor]** = vendor docs or blog, **[practice]** = professional standard or convention, **[claimed]** = single preprint or unverified summary. I read abstracts or HTML text for the sources below; where I only had a search summary I say so.

## 1. Summary

- **A deterministic check can only prove a figure is internally consistent, not that it answers the question.** Identities (line = qty x price, GP = revenue - COGS), partition sums and conservation checks catch arithmetic slips, fan-out, dropped rows and double counts. They cannot catch a wrong metric definition, a wrong filter or a mis-read period. Plan the verifier split around that boundary: code covers consistency, an LLM (rarely) covers fit.
- **Most checks can be generated from the claim itself, not written per dataset.** dbt `expression_is_true`, Great Expectations cross-column expectations and Looker data tests all show the form: a named assertion over a metric or relation ([dbt-utils](https://github.com/dbt-labs/dbt-utils), [GX expectations](https://greatexpectations.io/expectations/expect_column_pair_values_A_to_be_greater_than_B), [Looker assert validator](https://docs.cloud.google.com/looker/docs/ci-assert-validator)). These tools expect a human to author the rule [vendor]. For the harness the rule set is small and fixed (see section 3, P1 to P3), so code can derive every instance from the typed claim.
- **Partition and metamorphic checks are the strongest generic oracle for aggregates.** Ternary Logic Partitioning (TLP) splits a query by a predicate into TRUE / FALSE / NULL parts and checks that the parts recombine to the original. It found 175 DBMS bugs, 77 of them logic bugs ([Rigger and Su 2020, summary](https://neverworkintheory.org/2021/10/07/finding-bugs-in-database-systems-via-query-partitioning.html)) [measured, on DBMSs, not on LLM output]. The same trick applied to an analysis claim (sum of group sums + NULL group = total) catches the 243 k missing-customer-ID class of loss directly. I found no published use of it on LLM data agents.
- **A second, independent plan is only independent if it does not share the first plan's misreading.** N-version programming assumed independent failures; Knight and Leveson's 27-version experiment rejected that assumption at 99% confidence ([Knight and Leveson 1986](https://libraopen.lib.virginia.edu/public_view/jd472w463), via secondary summary). An LLM verifier that reads the same question and the same profile is a correlated version. A compiled plan from a typed operation shares the prepared view but not the analyst's code, so it is a better second version than another LLM.
- **LLM self-verification is unreliable on numbers; external, sound verification is reliable.** Without external feedback, GPT-4 on GSM8K dropped from 95.5 to 91.5 and 89.0 over two self-correction rounds ([Huang et al., ICLR 2024](https://arxiv.org/html/2310.01798v1)) [measured]. With a sound external verifier, GPT-4 gained on Game of 24, graph colouring and planning, while self-critique collapsed ([Stechly et al., ICLR 2025](https://iclr.cc/virtual/2025/poster/31014)) [measured]. A critical survey concludes self-correction works when reliable external feedback exists, such as code execution ([Kamoi et al., TACL 2024](https://arxiv.org/html/2406.01297)) [measured/survey].
- **Execution-based agreement signals are weak as a confidence score; an LLM judge adds signal on top.** On BIRD and Spider, string, structural and execution self-consistency and log-probability land at 0.61 to 0.68 AUROC for predicting a correct SQL, an LLM judge reaches 0.72 to 0.78, and a two-provider judge ensemble 0.82 ([selective-prediction study, arXiv 2607.06799](https://arxiv.org/abs/2607.06799)) [claimed: 2026 preprint, abstract only]. So the right split is arithmetic and structure by code, semantic fit by an LLM when risk warrants it.
- **Tolerance should be derived, not guessed, and every residual should be classified.** Floating-point sums legitimately differ by order: DuckDB documents multi-thread float differences and recommends `SET threads = 1` or ordering ([DuckDB docs](https://duckdb.org/docs/current/operations_manual/non-deterministic_behavior)) [vendor]. A 2026 oracle for SQL aggregates labels differences exact / bounded / indeterminate using a condition number rather than another engine's output ([arXiv 2609.00381](https://arxiv.org/abs/2609.00381)) [claimed]. The £2.5 k on £8.35 M residual is about 0.03%; whether that is rounding, a known defect or unexplained is a classification question, not a "chase it" question.
- **Audit and finance practice already has the right vocabulary.** Tolerable misstatement sits below materiality, and a separate "clearly trivial" level, "a smaller order of magnitude" than materiality, need not even be accumulated ([PCAOB AS 2810](https://pcaobus.org/oversight/standards/auditing-standards/details/AS2810), [AS 2105](https://pcaobus.org/oversight/standards/auditing-standards/details/AS2105)) [practice]. Neither standard fixes a percentage.

## 3. Patterns

Each pattern: what it moves from the LLM to code, evidence, cost.

**P1. Typed-claim identities (accounting identities as assertions).** The claim object carries the measure type (revenue, cost, GP, GP%, quantity) and the controller asserts the relations that hold by definition: GP = revenue - COGS; GP% = GP / revenue within rounding; GP <= revenue when the profile shows costs >= 0; units x unit price = line value at line level; ranks are consistent with the values; a "highest" claim really is the maximum of the returned table. Evidence: dbt, GX and Looker all ship this form [vendor]; no ablation on LLM agents. Cost: very low, a fixed list keyed to claim type. It needs the field-to-measure mapping already in `.pricing/context.md`.

**P2. Partition and conservation checks (TLP-style).** For any grouped claim, code re-runs the base aggregate without the grouping and checks: sum of groups + NULL-key group = total; filtered total <= unfiltered total (for non-negative measures) and filtered + complement + NULL-predicate part = total; row-count ledger (input rows - excluded rows by reason = rows used). Evidence: TLP's 175 bugs [measured, on DBMSs]. For data analysis the closest published line is metamorphic testing of text-to-SQL, e.g. SQLHD [claimed], plus a practitioner list of pipeline relations (permutation, partition union, scaling) in [one data-pipeline guide](https://qaskills.sh/blog/metamorphic-testing-data-pipelines-guide) and [a big-data MR formalism](https://repositorio.uai.edu.ar/items/a92aca83-90ca-4b74-b3ab-e001bd4fe7d4) [claimed]. Cost: one or two extra DuckDB aggregates, seconds. Catches fan-out (parts exceed total), silent row loss, NULL-key loss.

**P3. Independent recomputation from a compiled typed plan.** When the analyst's claim matches a typed operation (measure, group-by, filters, period; see 03, rec 2), code compiles a reference query from that spec and compares it with the figure the analyst's free-form code printed. This is differential testing with a deterministic second version. Evidence: execution agreement across candidates helps small models (+9 points over majority vote at 30 samples [measured], 1.5 to 3.5 for larger), but a single compiled plan is cheaper than sampling 30. Caveat from N-version work: shared assumptions (same prepared view, same period resolver) are shared failure modes. Cost: depends on the typed-op layer in 03; if that exists, near zero extra.

**P4. Execution replaces LLM arithmetic (program-of-thought discipline).** All figures in the reply bind to claim IDs produced by code; the model never types a number. Evidence: PoT and PAL gains [measured]; Grid-Mind shows the failure when numbers bypass tools [claimed]. The harness already does the binding in delivery. The extra check is mechanical: every numeric token in the draft reply must match an approved claim ID at the displayed rounding. Cost: low.

**P5. Reconciliation with derived tolerance and residual classification.** Compare the analyst's figure with the reference using arithmetic in exact types where possible (DECIMAL or integer pence; DuckDB documents float order effects [vendor]). Then classify any residual:

1. *Rounding:* |diff| <= n_rounded_terms x half the displayed unit (e.g. 0.5p per line, plus a float bound of about 1e-9 relative for DOUBLE sums, or the condition-number bound in [arXiv 2609.00381](https://arxiv.org/abs/2609.00381) [claimed]). Pass silently.
2. *Explained by a registered defect:* the residual equals the sum of values on rows the issue register (02) flags and the analysis excluded or treated (blank-cost lines, `POST`, duplicates) within rounding. Pass with a note. This is the finance practice of reconciling items, not just totals.
3. *Below clearly-trivial:* |diff| / total below a configured trivial level (audit standards call for "a smaller order of magnitude" than materiality; no number is mandated [practice]). Note, do not repair.
4. *Between trivial and tolerable:* disclose as a caveat with the amount.
5. *Above tolerable, or unexplained in sign or direction:* escalate (targeted LLM verifier or ask the user).

Evidence: Datafold's absolute/relative tolerance modes, BlackLine/Trintech tiered tolerances and auto-certify [vendor]; AS 2105/2810 ordering of tolerable < material and clearly trivial [practice]. Cost: a tolerance table (defaults in code, overridable per measure in `.pricing/context.md`) plus the register join. Percentages: no authority gives them; treat any default as a policy choice to be confirmed with the user.

**P6. Question-level metamorphic relations on the agent (consistency, not correctness).** Re-ask a paraphrase or permuted-row version and compare figures. SQLHD reports F1 69 to 83 on text-to-SQL hallucination detection [claimed]. Costs a full second LLM run, so it contradicts the speed goal; useful offline as a regression test across Luna, Sonnet and Flash runs, not at runtime.

**P7. Query equivalence provers (VeriEQL, SQLSolver, SpotIt).** They check two SQL texts are equivalent, with bounded or fragment limits (no window functions in VeriEQL per the [SpotIt paper](https://arxiv.org/pdf/2510.26840), no counterexamples from SQLSolver) [claimed]. The analyst writes Python and DuckDB rather than one clean SQL, so these do not fit.

**P8. LLM verifier, narrowed.** Used for what code cannot test: whether the metric definition, filter, period and scope match the question and the confirmed context. Evidence for its residual value: judge AUROC 0.72 to 0.78 vs 0.61 to 0.68 for execution agreement [claimed]. Evidence against using it for arithmetic: intrinsic self-verification degrades accuracy [measured]. Judges also miss errors they share with the generator and are prompt-sensitive ([Judging the Judges](https://arxiv.org/html/2406.12624) [measured]).

## 4. Relevance to the pricing harness

- **Reconciliation failures routing to full review (the £2.5 k on £8.35 M case):** P5 turns "exact tolerance fails" into a classified residual. If the residual matches the flagged-row value (the `POST` and `TEST001` lines, 2,138 uncosted lines, duplicate repeats), it is "explained" and closes in code. This directly addresses the minutes spent chasing it.
- **Verifier at 100 to 180 s per pass:** P1 to P4 run in seconds and cover the arithmetic that the verifier currently recomputes. The LLM verifier then runs only on claims P1 to P5 cannot clear (section 5).
- **Fan-out from duplicate master keys and 243 k missing customer IDs:** P2 catches both: group sums + NULL group must equal the total, and join row-count ledger must match.
- **Run-to-run drift (85123A blank UoM):** deterministic checks do not stop the analyst choosing differently, but P1/P5 make a different choice visible as a different excluded-value amount and a different classification. The decision itself belongs in the stored handling (workstream 5).
- **Float order effects:** two runs with different thread timing can differ in the last digits on DOUBLE sums. Casting money to DECIMAL (or integer pence) before summing makes the verifier comparison exact; I could not confirm DuckDB's DECIMAL sums are thread-order independent from a primary source, but fixed-point integer sums are associative by construction. Test it once.
- **Partial current quarter and period logic:** not an arithmetic error. Only a period resolver in code (03, rec 6) or the LLM verifier would catch it.

## 5. Recommendations

Simplest first.

1. **Adopt: claim-type identities and sanity checks (P1).** Fixed list keyed to measure type; zero LLM. Highest value per line of code. Include "highest/lowest/top-N claim equals the max/min/ordering of the returned table".
2. **Adopt: ledger and partition sums on every grouped claim (P2).** Sum of groups + NULL group = ungrouped total; row-count ledger closes. Run in the controller, not by the analyst.
3. **Adopt: residual classification before routing (P5).** Five classes above; only class 5 reaches full verification. Use exact decimal arithmetic and a rounding bound derived from the number of rounded terms. Join residual to the issue register values (02) for the "explained" class.
4. **Adopt: mechanical figure binding check on the reply (P4).** Every numeric token traces to an approved claim ID at displayed precision.
5. **Try: compiled reference plan for claims that fit a typed operation (P3).** Only after the typed layer in 03 exists. Compare to the analyst's printed figure with the P5 tolerance. Expect common-mode failures with the analyst on shared definitions; do not treat agreement as proof of semantic fit.
6. **Try: risk-routed LLM verifier (P8).** Run the LLM verifier only when at least one holds: (a) claim not expressible as a typed op and so no reference plan; (b) a class-5 residual; (c) the register shows an unresolved high-severity issue touching the claim's columns with no stored handling; (d) the question changes a definition or scope the confirmed context does not cover; (e) the user asked for a high-stakes export. Give it a narrow brief (definition, filter, period, scope against context) and no authority to redo arithmetic. Everything else gets "none / note".
7. **Try: offline metamorphic regression suite (P6).** Paraphrase and row-order variants across Luna, Sonnet and Flash runs on the six-turn conversation, to measure run-to-run consistency. Not at runtime.
8. **Skip: LLM judge for numeric agreement, multi-sample voting at runtime, SQL equivalence provers.** The first is unreliable where arithmetic matters; the second adds latency; the third does not fit Python/DuckDB analysis code.

## 6. Open questions and weak evidence

- **No published ablation of deterministic checks versus an LLM verifier on a data agent.** The comparisons I found are on text-to-SQL (selective-prediction AUROC), math (self-correction) and DBMS bug-finding (TLP). Transfer to pricing claims is inferred.
- **Several 2026 sources are single preprints** (selective-prediction study, SQLHD, SpotIt, condition-aware aggregate oracle, Grading the Grader, Grid-Mind). I read abstracts or search summaries, not full text. Treat their numbers as directional until checked.
- **Knight-Leveson was read through secondary summaries.** The qualitative point (correlated failures) is well established; the exact figures are not verified here.
- **No authority fixes tolerance percentages.** Audit standards give an ordering (trivial < tolerable < material) and conventions, not values. Defaults must be set by the user or product policy; I do not recommend a number.
- **Coverage of the arithmetic checks depends on the field-to-measure mapping** being confirmed. If the mapping is wrong (e.g. cost in the wrong UoM), identities hold on wrong inputs. That is the unit/currency gap noted in 02, which has the weakest detection evidence.
- **Semantic-fit errors remain the unsolved part.** The selective-prediction signal for these is the LLM judge, at AUROC well below 1. How often a wrong filter or period slips past P1 to P5 on this pack is unmeasured; it should be the first thing the benchmark in 01 (rec 3) records.
- **DuckDB DECIMAL determinism across thread counts** is unconfirmed from a primary source (section 4).
