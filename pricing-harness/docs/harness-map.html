What the harness ships

This map covers every file in the shipped package (the files list in package.json plus the src/ that builds into dist/), leaving out tests, evals and their scripts. It covers what each file does, which files it calls, and what runs where while a user waits for an answer. I wrote it by reading the code itself. Where docs/architecture.md disagrees with the code, the code wins, and the loose ends section lists the gaps.

01 · System

Four kinds of process

The browser talks only to one local Node server. Each question forks a fresh worker process that runs the AI agent. The worker starts Python processes for SQL, scripts and data checks. Everything durable lives as files in the business workspace folder.

Solid lines are calls inside your machine. Dashed lines cross a process boundary that matters: the forked worker, and the only traffic that leaves the machine (model calls, plus one price lookup when the model is resolved). The four solid lines on the right are, top to bottom: query → the SQL process, execute_analysis → record_execution, data findings, and profiling. The bash tool runs a real shell with credential variables removed from its environment. It is not a sandbox.

02 · One question, end to end

What happens when the user presses Enter

Follow one question from the composer to a delivered answer. Every step names the file that does it.

Boot (once, at server start)

  1. Read settings and check the machine

    harness.config.json is parsed strictly (an unknown key is an error) and turned into PRICING_* variables. Real environment variables win. Python is checked by importing duckdb, pandas, openpyxl. Credentials are checked through Pi's model runtime. An unknown model ID borrows connection settings from a catalogue model of the same vendor and gets its price from OpenRouter's public list.

    settings.ts → runtime.ts (loadConfig, resolveModel, checkRuntime) · defaults.ts

  2. Validate the bundle and fingerprint it

    Checks that versions.json matches plugin.json, that every skill and knowledge card has name/description frontmatter, that there are no symlinks and that every relative markdown link resolves. Then it hashes every bundled file into one fingerprint. A changed fingerprint makes every conversation start a fresh analyst session.

    agent/bundle.ts (validateBundle)

  3. Open the workspace and restore the last conversation

    Creates files/ .pricing/ analyses/ outputs/, adopts any files already sitting in files/, marks runs left "running" by a crash as interrupted, and reloads the conversation that was open. Its charts are rebuilt from frozen checkpoints, or replaced by a notice if the evidence changed.

    workspace.ts · files.ts (openFileStore, loadRuns) · conversations.ts · exploration-restore.ts · application.ts
Submit

  1. Browser posts the question

    The composer sends {requestId, text, fileIds: []} to POST /api/messages. An empty fileIds means "use every source in the workspace". The UI already listens on /api/events (server-sent events) and applies each event to its snapshot.

    ui/App.tsx · ui/api.ts · ui/useSession.ts · routes/chat.ts

  2. RunController accepts it

    Rejects bad input, a second question while one is running (409) and a machine that isn't ready (503). The same requestId twice returns the same run, so a retried POST cannot start two runs. It re-hashes every source, writes analyses/<run>/run.json, appends the user message and saves the conversation.

    agent/runs.ts (submit, start) · events.ts (setRun, appendLogical)
Prepare the turn

  1. Fresh session or follow-up?

    The session key is a hash of the bundle fingerprint and every source's path and hash, stored in state.json. If the key matches, this is a follow-up: the prompt is just the question and a deadline. If it doesn't, the analyst folder is wiped and a full prompt is built.

    workflow/orchestrator.ts (executeWithLog)

  2. Profile and scan the data (fresh sessions only)

    Each CSV/XLSX is loaded into a cached DuckDB file (all text columns) and profiled: inferred types, blanks, ranges and frequent values. The seven detectors then flag suspect rows: parse, shape, domain, uniqueness, identity, time and peer ratio. Both results are cached by file content and trimmed to fit the prompt (40k and 12k characters). A detector failure is logged and never blocks the run.

    source-profiles.ts → profile_source.py · data-findings.ts → data_findings.py · data_workspace.py

  3. Build the first prompt

    Question, working folder, Python path, deadline (budget minus one minute), context.md, source list, path to the profiles file, the full text of three preloaded method files (the routing skill, shared rules and metric verification) and the compact findings.

    workflow/stage-prompt.ts (buildStagePrompt, PRELOADED)
The analyst works (in a forked worker)

  1. Fork the worker

    StageRunner forks worker.js in its own process group and sets a kill timer for the remaining budget. Before each model call, tool call or retry, the worker asks the parent over IPC for a go-ahead. The parent debits the budget (900 s, 100 model calls, 150 tool calls, 2 retries) and refuses once a limit is spent. It also stops the run after three identical operation/result pairs, or when usage data goes missing.

    stage-runner.ts · budget.ts (WorkflowBudget) · worker.ts (gate)

  2. Start the Pi agent session

    The analyst system prompt is the short one in role-prompts.ts. Pi lists the 7 pricing skills, analysis-visualize and every knowledge card by name and description. User extensions, context files and themes are switched off. The session is resumed from .pricing/workflow/<conversation>/analyst/sessions on follow-ups. Compaction starts when 40% of the context window is still free.

    session.ts (createPricingSession) · role-prompts.ts

  3. Tools the analyst can call

    query: SQL against a long-lived DuckDB process with one typed view per source or sheet. Results show up to 100 rows, and save writes the full result to a CSV. execute_analysis: runs a Python file under record_execution.py, which logs every workspace file the script opened. bash / read / write / edit: the Pi built-ins. Python run through bash is logged too. present: names a recorded CSV, its columns and a chart type. Every query and script leaves an execution-*.txt in the analyst folder, and those files are the evidence used later.

    query-tool.ts → query_server.py · worker.ts (execute_analysis, present) · shell-evidence.ts · supervised-shell.ts · tool-input.ts

  4. Hooks watch every step

    Hooks block the first calculation until a task skill and a knowledge card have been read. They hold a script that reads a source file directly, block pip install and keep context.md append-only. They also block copy-pasted scripts, add SQL error fixes and plugin lint hints, warn about slow or repeated SQL, stop a tool call that grows past 40k characters, and add a "time left" line under each tool result. Inside the SQL process, same_rows can stop a statement whose combined totals cover different rows, and peer_ratio and offsets add notes about outlier rows and returns.

    nudges.ts (HOOKS) · same_rows.py · peer_ratio.py · offsets.py

  5. Provider hiccups

    A transient failure (429, timeout, 5xx and so on) is retried in the same session with "continue from where you stopped", at most twice. A stopped runaway call is retried once with "issue it again shorter". The final assistant text is sent back to the parent.

    transient-error.ts · worker.ts (read)
Check and deliver (back in the server)

  1. At most one nudge turn

    The parent may send one more message to the same session. It does this when the analyst computed something but replied with only a question, or when a plugin lint on the reply fires (for example, a rate written as 0.123 instead of a percentage).

    orchestrator.ts · reply-figures.ts (withheldResult) · nudges.ts (lintHints) · lints.json

  2. Figure check

    Every number in the reply with 3 or more significant digits must appear in some executed output, at the reply's precision. A printed fraction shown as a percentage counts, and so does the difference of two supported numbers. If any don't match, one recheck turn runs. Numbers still unmatched are delivered with a notice that names them.

    reply-figures.ts (unverifiedFigures) · stage-prompt.ts (recheckPrompt)

  3. Seal and bind views

    If the analyst called present, the CSVs it named must be unchanged outputs of an executed query or script. They are copied into checkpoints/<id>/ with their hashes. Tables and charts are then built from those frozen copies, so displayed values come from files, never from model text.

    checkpoints.ts (sealPresentation) · workflow/exploration.ts (normalizeExploration, bindExploration)

  4. Deliver, then re-verify

    The reply, any notice and the bound views go to the chat. Afterwards the checkpoint and every source are hashed again. If anything changed, the views are withdrawn and the run is marked "no verified answer". Logs are written to events.jsonl and steps.jsonl with secrets redacted.

    orchestrator.ts · runs.ts (finish) · delivery.ts · event-log.ts · steps.ts
03 · Every shipped file

File by file

Line counts are from the working tree. Files with a coral edge are the core of the product: read them first. "→" shows what a file calls or depends on.

Server shell

src/ · 1,130 lines

Boots the app, reads settings, serves HTTP and owns the workspace folder. Contains no AI logic.

src/server.ts79 lines

Entry point for npm start. A Fastify server bound to 127.0.0.1. It rejects any request whose Host or Origin isn't the local address (the API has no login, so this is the only access control), maps errors to JSON, sets a strict Content-Security-Policy so the UI can't load outside URLs, and serves the built UI from dist/ui.

→ application, routes/chat, routes/files
src/application.ts39 lines

The composition root. Builds every long-lived object in order: workspace, file store, bundle check, health check, model, root agent session, EventView, restored conversation and RunController. Shared by the web server and the headless CLI.

→ runtime, workspace, files, conversations, bundle, session, events, runs
src/runtime.ts149 lines

loadConfig turns environment variables into a typed config. Workspace, model, Python and provider are required, and paths must be absolute. resolveModel picks the model in Pi's catalogue, accepts newer IDs by copying a same-vendor template, fetches a price from OpenRouter, and caps output at 32k tokens per call. checkRuntime reports whether Python and credentials are ready.

→ settings, defaults, Pi ModelRuntime, openrouter.ai
src/settings.ts102 lines

Strict reader for harness.config.json. It rejects unknown keys and bad types, then maps each value to a PRICING_* variable. Real environment variables override the file. PRICING_CONFIG_FILE can point at another file.

→ defaults
src/defaults.ts4 lines

Built-in fallbacks: providers openrouter and openai, the thinking levels, and default limits of 900 s, 100 model calls and 150 tool calls.

src/contracts.ts110 lines

Types shared by the server and the browser: source files, run records, chat messages, steps, the session snapshot and the event union sent over SSE. Also HarnessError, which carries an HTTP status.

src/exploration.ts49 lines

Shape of an in-chat "exploration": tables, which select columns from a result CSV, and charts (line, bar, stacked, waterfall, scatter). Also the hard limits: 4 tables, 4 charts, 12 columns, 1,000 rows, 5,000 cells, 1 MiB.

src/workspace.ts120 lines

The folder layout and the safety primitives everything else uses. safePath refuses paths and symlinks that leave a root. atomicJSON writes to a temp file then renames it. hashFile computes SHA-256 and caches it while device, inode, size, mtime and ctime are unchanged. It also creates the starter context.md.

src/files.ts234 lines

Source store. It streams an upload into files/<uuid>/ with a size cap, accepts only CSV, XLSX, TXT and MD, keeps files.json, and can re-hash every source or report which ones changed. It also holds an "artifacts" registry for outputs/, but nothing ever registers an artifact (see loose ends). loadRuns marks runs a crash left as "running" as interrupted.

→ workspace
src/conversations.ts67 lines

Saves each conversation's visible chat to .pricing/workflow/<id>/conversation.json, with a title taken from the first question. current.json remembers which one to reopen. Lists conversations for the sidebar, newest first, and moves the old single-file format into a folder once.

→ workspace
src/headless.ts96 lines

CLI with no browser (npm run headless). --status prints the model and health, --question "…" runs one turn, and otherwise it reads JSON lines from stdin (submit, cancel, close) and prints every event as JSON. The evals drive the harness through this file.

→ application
src/routes/chat.ts51 lines

The chat API: GET /api/session (snapshot), POST /api/messages, /api/cancel, /api/session/new, GET /api/conversations, POST /api/conversations/:id/open, GET /api/status, and GET /api/events, an SSE stream with a 15 s heartbeat.

→ RunController, EventView
src/routes/files.ts30 lines

GET/POST /api/files for sources (uploads are refused while a run is busy). GET /api/outputs/:id downloads an artifact after checking its hash, and serves HTML inside a sandboxing CSP.

→ files

Agent core

src/agent/ · 641 lines

Wraps the Pi agent SDK and owns the run lifecycle and UI state.

src/agent/runs.ts262 lines

RunController. Allows one run at a time and makes submits idempotent by requestId. It snapshots sources, writes run.json, creates a WorkflowOrchestrator per question and wires its callbacks (message, step, checkpoint, invalidate). When the run finishes, it fails the run if any source changed. It also handles cancel, new conversation, opening a saved conversation, and close.

→ orchestrator, stage-runner, source-profiles, data-findings, events, conversations
src/agent/events.ts176 lines

EventView: the server's copy of what the UI should show (messages, runs, active steps, busy flag), with a sequence number on every event so the browser can drop stale ones. A settled event carries the whole snapshot.

→ contracts
src/agent/session.ts119 lines

Builds a Pi agent session with only the bundled skills: user extensions, prompt templates, themes and context files are all off. It checks that the loaded skills match the bundle exactly, refuses model or reasoning-level fallback, and tags the session with the bundle fingerprint. analysisEnvironment strips any variable named like a key, token, secret, password or credential before a shell or Python process starts.

→ Pi SDK, workspace, bundle
src/agent/bundle.ts84 lines

Validates bundled/ and computes its fingerprint (see Boot, step 2). It also registers each knowledge card as its own "skill", so the agent sees every card's name and description on every turn.

Workflow: the analyst loop

src/agent/workflow/ · 2,518 lines

Runs one analyst turn, constrains it and checks what comes out. Most of the product's behaviour lives here.

orchestrator.ts219 lines

The per-question script: decides fresh or follow-up, profiles and scans sources, builds the prompt, runs the turn, applies at most one nudge turn and one figure recheck, seals and binds views, delivers the reply, then re-verifies evidence and sources. Any failure becomes a short user-facing message and a "no verified answer" outcome.

→ stage-prompt, stage-runner (via Runner), reply-figures, nudges (lints), checkpoints, exploration, event-log, steps, delivery
worker.ts411 lines

Runs in the forked child process. It defines the execute_analysis and present tools, wraps bash so Python runs are logged, starts the SQL tool, creates the analyst session with the hooks, and wraps model streaming and tool calls in the budget gate. It also limits write/edit to the analyst folder plus context.md, reports usage and timing, and retries transient failures.

→ session, query-tool, nudges, shell-evidence, supervised-shell, transient-error, exploration, record_execution.py
stage-runner.ts108 lines

Forks worker.js (or worker.ts via tsx in dev), passes budget gate requests and answers over IPC, enforces the deadline, and kills the whole process group on finish, cancel or timeout after a 2 s grace.

→ budget
budget.ts78 lines

WorkflowBudget: counts model calls, tool calls and retries (at most 2) against limits and a wall clock. It stops the run after 3 identical operation/result pairs or when the SDK fails to report usage. It also adds up estimated cost for run.json.

nudges.ts429 lines

The 13 behaviour hooks, installed as one Pi extension: skill-read, source-read, focus-thinking (reasoning level drops after the first analysis), no-installs, context-append-only, reuse-scripts, error-hints, plugin-lints, slow-query, repeated-sql, runaway-stream and pacing. Each can be switched off with PRICING_HOOKS_OFF. Also loads lints.json from the plugin.

→ lints.json, skills folder
query-tool.ts199 lines

Starts query_server.py once per turn and talks to it in JSON lines. Defines the query tool, whose description lists every view and its columns. Formats results as markdown tables and records each call as query-*.sql + execution-*.txt evidence. A saved CSV becomes presentable.

→ query_server.py
reply-figures.ts38 lines

The numeric honesty check (see "Figure check" above). Also withheldResult, which spots a reply that asks a question and shows no figure.

checkpoints.ts66 lines

sealPresentation copies presented CSVs into a checkpoint folder and writes checkpoint.json with every hash. loadCheckpoint re-verifies all of them. stableRefs checks that a list of files still has the same hashes.

→ workspace
exploration.ts221 lines

Validates what the analyst passed to present, dropping bad tables or charts with a reason. Includes a small CSV parser, and builds the delivered tables from the frozen files. Blank cells are "held", numbers are "approved", and text cells can't be charted.

exploration-restore.ts30 lines

When a saved conversation is opened, rebuilds each message's tables and charts from its checkpoint, or replaces them with a "could not be restored" notice.

stage-prompt.ts74 lines

Text of the first-turn prompt, the follow-up prompt and the nudge/recheck messages. PRELOADED lists the three method files whose full text goes into the first prompt.

role-prompts.ts6 lines

The analyst's system prompt (one paragraph of working rules plus how to treat harness notes), the base tool list, and harnessNote, which wraps harness messages in <harness-note> tags so the model can tell them from the user.

source-profiles.ts141 lines

Calls profile_source.py per CSV/XLSX, caches results in memory by hash, and packs them into a compact column-row form. Sample values, then columns, are dropped until it fits in 40k characters.

→ profile_source.py
data-findings.ts72 lines

Calls data_findings.py on all CSV/XLSX sources and compacts the result to 12k characters, interleaving detectors so each keeps its top findings. Always keeps "gaps" (sources or checks that could not run), so a skipped check never reads as clean data.

→ data_findings.py
steps.ts179 lines

Turns worker events into the step list the UI shows ("Ran x.py", "Query: SELECT…", "Thinking"). Summaries are fixed wording built from tool arguments, never model-written text.

shell-evidence.ts44 lines

Wraps the bash tool: a successful command that runs python is saved as bash-*.sh + execution-*.txt, and CSVs it wrote become presentable.

supervised-shell.ts29 lines

Runs bash commands as plain child processes inside the worker's process group, so killing the worker kills them. The comment states it is not a sandbox.

transient-error.ts27 lines

Recognises retryable provider errors and holds the "continue" and "issue it shorter" messages used for retries.

model-timing.ts38 lines

Per model call: wait at the gate, time to first token, generation time and tokens per second. Written to the event log.

event-log.ts35 lines

Append-only JSONL writer that serialises writes so lines never interleave. Truncates long strings and replaces the values of secret-named environment variables with [REDACTED].

contracts.ts51 lines

Types for the worker protocol: StageRequest, StageResult, Execution (script + output + files read), Checkpoint, Runner.

delivery.ts10 lines

Maps an internal failure reason to one of four user-facing sentences.

tool-input.ts13 lines

Schema for the execute_analysis argument. It must be an absolute path, not a shell command.

Python data tools

bundled/harness-tools/ · 1,460 lines

Run with the venv's Python. The docstrings commit to "facts only, no business definitions": code flags and counts, and the analyst or user decides.

query_server.py284 lines

The long-lived SQL process. Attaches each prepared source and creates a typed view per file or sheet, then locks DuckDB: external access is off, the only allowed directory is the analyst folder, and configuration is locked. Only certain statement kinds run (SELECT/WITH/DESCRIBE/SHOW/SUMMARIZE/EXPLAIN/VALUES/CREATE VIEW or TABLE/DROP/COPY). TEMP is rewritten to permanent so definitions last the conversation. Runs batches, returns 100 rows, saves CSVs, and calls the three SQL checks.

→ data_workspace, same_rows, peer_ratio, offsets, data_findings (peer columns)
data_workspace.py219 lines

Shared base. prepare_source loads a CSV (strict parsing, delimiter sniffed, UTF-8 only) or one XLSX sheet into a DuckDB raw table with all-text columns. The result is cached by content hash, import options and tool versions, and written atomically. profile_prepared computes column facts, and create_typed_view casts a column only when no present value would be lost.

data_findings.py309 lines

Seven detectors (VERSION 10): D1 values that fail the column's main format, D2 spelling or shape variants, D3 keys missing from a reference, D4 duplicates, D5 a column that should equal a product of two others, D6 future or reversed dates, D7 values a power of ten, ×12 or a sign away from their group median. Writes findings.json + flags.parquet (finding → row id) and caches by content.

→ data_workspace
same_rows.py227 lines

Runs before a statement. When one expression combines aggregates of different columns (sum(sales) - sum(cogs)), it counts the rows that only one side covers because of NULLs or FILTERs. It may stop the statement and explain. Parses SQL through DuckDB's own JSON form of the query.

peer_ratio.py157 lines

Runs after a statement. If rows far (≥5×) from their key's median carry ≥0.5% of a summed total, it adds a note. Uses the column/key pairs that data_findings judged well described by a median.

offsets.py115 lines

Runs after a grouped sum of a whole-number column. It notes groups where negative rows (returns) cancel ≥50% of positive ones while the net stays positive, because per-unit values there rest on little net volume.

record_execution.py122 lines

Runs a generated script via runpy with a Python audit hook, recording every file it opened for reading and every DuckDB statement (including paths in SQL strings). Writes a provenance JSON. The docstring says plainly that this is evidence, not a sandbox.

profile_source.py27 lines

CLI wrapper: prepares and profiles one CSV, or up to 10 sheets of an XLSX, and prints JSON.

→ data_workspace
data-analysis.md7 lines

A short data guide the agent can read: the query tool, the "reduce → compute → revise → show" pattern, reserved words, and how to use findings.json/flags.parquet.

06 · Loose ends

Things I noticed while reading

None of these breaks the main path, but each one is code or text that doesn't match what the product does today. Listed roughly by how much they could surprise you.

bash bypasses the write guard and the context.md rule

The write limits and the append-only rule cover only the write and edit tools. The analyst also has bash in the workspace with your user's permissions, so it can write, delete or overwrite context.md or any file you can. The only protections are credential stripping, the install regex and the process-group kill. The code says this plainly, but the product docs should say it too.

docs/architecture.md describes a retired design

It talks about handoff.json, emit_handoff, claim approval and checked-figures.ts. None of these exist. Checkpoints are now created by the present tool. It also says "five detectors" (the code has seven), "Pricing Plugin 0.4.3" (0.4.11) and "Workflow 3.0" (versions.json says 2.2.0). This file ships to users.

The root agent session is never prompted

application.ts creates a full Pi session with its own long system prompt and a workspace-wide bash tool, but nothing ever calls prompt() on it. In practice it only mints the conversation ID. Its prompt text in session.ts is dead text that still mentions a "present tool" and documentation reading.

The artifact/outputs path is half-removed

files.registerPublishedRun is never called, so /api/outputs can only ever serve artifacts from older workspaces. Meanwhile the plugin's shared rules tell the agent to follow html-reporting.md for circulated reports, while worker.ts blocks report commands with "report generation is retired". The two contradict each other.

Smaller items

· harness.config.json ships an evaluation block that points at a plan file under docs/superpowers/.
· playwright is a runtime dependency, which adds a browser download to installs that don't need one.
· piSdk: '1.0.4' is hard-coded in three places (runs.ts, routes/chat.ts, versions.json).
· resolveModel runs at boot, in the health check and again in every worker turn. With an ID outside the catalogue, each run fetches OpenRouter's model list (10 s timeout).
· The figure check skips any bare 1900–2100 number as a year (noted in the code).
· Data findings and profiles are computed only on fresh sessions. A follow-up after the user confirms a treatment reuses the first scan, which is intended but worth knowing.
· peer_ratio and offsets check only SQL. Sums done in Python aren't checked, as their docstrings say.
